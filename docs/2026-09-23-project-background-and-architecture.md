## 第一题：项目背景、使用人群、人工流程、产品价值与效果

### 1. 项目是什么？

**Live Make 是一个面向企业内部内容团队的智能视频创作平台，当前核心创作场景明确为固定 AI 虚构人物出镜的知识讲解视频。**

用户提交创作需求和基础资料后，由一个主管 Agent 自主组织多个专业子 Agent，完成资料整理、脚本创作、视频制作与质量检查，并在关键阶段交由人工审核，交付视频后由用户选择手动发布或系统代发到抖音。

项目的核心不是“调用一次模型生成视频”，而是：

> 把一项视频创作任务，交给一支具有明确分工、专业操作方法和受控工具权限的智能体团队完成。

当前设计保留一种创作入口：**从零创作，从需求和资料出发，完成脚本与视频。** 后续已确认支持抖音手动发布和系统代发；成片批准与发布确认分开，不能因审批通过就自动发布。

主管可以自主调整执行安排，但不能绕过审批、权限和预算限制。

#### 本轮确认：知识讲解与固定人物

| 项目 | 已确认要求 |
|---|---|
| 内容形态 | 知识讲解，不以商品展示、带货或物品操作为默认需求 |
| 人物来源与数量 | 一个 AI 创作的成年虚构人物开口讲述，不以复刻某个真人为目标 |
| 跨视频使用 | 不同视频沿用同一个人物，形成固定账号形象 |
| 外观方向 | 接近真人的写实风格，美丽、性感、成熟的成年女性，不走卡通路线 |
| 声音方向 | 成熟、温暖、清晰、自然的女声，语速适中、有亲切感，不刻意使用气声，不模仿某个真人 |
| 表现要求 | 人物自然说话，配合表情、点头和手势，不要求逐个手势按指定时刻精准执行 |
| 辅助画面 | 可按内容需要加入字幕、图片或示意图，不要求每条视频都包含全部形式 |

大白话：**每条视频讲不同知识，但由同一位虚构讲解者自然讲述，不是只有背景旁白，也不是必须拿着物品演示。**

固定人物是目标，不是模型已经保证跨视频一致。具体年龄、脸型、发型、服装、背景、实际音色、生成模型和知识领域尚未定稿；无需在补充七题时逐一确定。声音风格已确认，具体固定音色与绑定方式待实施设计。

### 2. TOB 还是 TOC？

既有定位是**服务于企业内部内容团队的生产力工具，属于企业侧使用场景**，而不是面向大众消费者的视频娱乐产品。本轮确认的是视频内容与人物表现形式，不据此擅自把使用对象改为 TOC；若后续调整为个人创作者产品，应另行明确。

| 身份 | 是谁 | 与产品的关系 |
|---|---|---|
| 使用组织 | 媒体、内容服务公司、品牌企业等 | 组织内容生产，承担使用和管理成本 |
| 直接用户 | 编辑、策划、运营、制作与审核人员 | 操作 Live Make 完成工作 |
| 内容受众 | 最终观看视频的人 | 消费视频内容，不一定使用 Live Make |

**当前不默认建设多租户 SaaS。** 对外售卖、客户独立登录、计费和租户隔离不属于已确认能力。企业内部使用与对外商业化 TOB 产品需要区分。

### 3. 当前核心场景与三种业务参考

当前以固定虚构人物的知识讲解为核心。以下三种场景保留为业务参考与扩展，不再作为默认制作要求，也不要求知识视频出现商品。它们**共用一套 Agent 架构，通过不同资料、规则和模板适配**，不是三套系统或三个真实客户。

#### 3.1 科技资讯短视频：参考 36氪

科技内容团队将有依据的资讯整理成简短视频。

- 使用者：内容编辑、视频运营、责任编辑。
- 输入：选题方向、官方公告、原始资料、可用素材。
- 输出：经审核的科技快讯视频。
- 重点要求：事实准确、来源可追溯、信息具有时效性，不遗漏关键条件。

示例：根据某项产品更新的官方资料，制作一条只讲一个核心信息点的短视频。

这里最重要的不是“搜到了多少资料”，而是**脚本中的关键陈述是否有依据**。

#### 3.2 客户内容交付：参考新榜

内容服务团队根据客户需求，为品牌制作短视频。

- 使用者：项目负责人、内容策划、制作人员、内部审核人。
- 输入：客户需求说明、品牌规范、授权素材、交付要求。
- 输出：符合需求的短视频及交付记录。
- 重点要求：需求对齐、品牌表达一致、修改意见与内容版本对应。

示例：根据客户提供的活动说明和品牌资料，制作一条活动预告视频。

当前设计不默认提供客户外部审批门户。**内部审核通过不自动等于客户验收通过**；如需客户确认，应明确记录其对应版本。

#### 3.3 商品营销短视频：参考三只松鼠

食品品牌的内部团队，根据确认后的商品资料制作宣传视频。

- 使用者：电商运营、品牌内容人员、商品信息确认人员、审核人员。
- 输入：商品资料、真实图片、活动条件、品牌规范。
- 输出：商品展示或营销短视频。
- 重点要求：商品属性准确、包装与素材一致、卖点有依据、活动信息有效。

示例：根据一款礼盒的商品说明和图片，制作一条约 12 秒的展示视频。

**商品资料是事实依据，网络热点只能辅助表达，不能用于猜测商品属性。**

### 4. 不使用产品时，人工通常怎么完成？

以下是为项目建立的**人工工作流程模型**，不是对上述公司的实际内部流程作断言。

| 环节 | 人工工作 | 交付物 |
|---|---|---|
| 明确需求 | 确认受众、目的、主题、时长、风格和交付要求 | 创作需求单 |
| 整理资料 | 阅读资料，查找来源，核对事实，整理素材 | 资料包与素材清单 |
| 编写文案 | 选择表达角度，组织内容 | 视频文案 |
| 设计镜头 | 规划讲解者出镜、每段台词和辅助画面；自然动作不必逐个编排 | 镜头表 |
| 准备讲解者 | 沿用人物参考，准备声音，核对知识依据与讲解节奏 | 人物引用、声音设定与台词音频 |
| 审核脚本 | 检查事实、表达、需求符合度和画面方案 | 批准的脚本版本 |
| 制作视频 | 准备素材、配音、字幕、剪辑与合成 | 视频初版 |
| 检查修改 | 检查画面、声音、字幕，定位问题并修改 | 修订视频 |
| 审核交付 | 确认最终版本，整理文件和记录 | 经批准的成片 |
| 发布与记录 | 下载后自行发布，或确认授权账号及设置后代发 | 发布记录、链接或回执、核实状态 |
| 观察表现 | 在固定观察窗口查看可获取的数据 | 发布及观看互动记录 |

- **文案：**视频要说什么。
- **镜头设计：**每个时间段给观众看什么、听什么，也就是文字分镜，不要求必须画图。
- **制作方案：**具体使用哪些素材与工具，怎样把镜头做出来。

### 5. 产品带来什么价值？

#### 5.1 减少重复性操作

预期由 Agent 和工具辅助完成资料整理、初稿编写、素材组织、配音、字幕、合成和检查，减少人工搬运信息与重复制作。

#### 5.2 减少环节之间的协调成本

主管统一理解需求、分派工作、检查交付并汇报进度，降低“谁在处理、卡在哪里、应该退给谁”的沟通成本。

#### 5.3 让内容与处理过程可追溯

将需求、事实依据、脚本版本、成片版本、审查报告与审批记录关联起来，减少“审核的是旧版本，制作却用了新版本”的混乱。

#### 5.4 保留人的关键判断

系统辅助创作和检查，人工保留脚本、成片等关键审批权。遇到资料缺口、重大不确定性或超限时暂停，而不是强行给出结果。

#### 5.5 复用专业操作方法

将专业 SOP 封装为 Skills，让不同任务复用同一套方法，当前优先使用知识讲解规则，并保留资讯、客户交付和商品营销的场景模板。

### 6. 效果如何？

**目前可以说明预期价值，不能宣称已经实现具体的提效、质量或商业增长。**

| 效果方向 | 后续应验证什么 |
|---|---|
| 效率 | 同类任务的人工投入时间、总交付时间是否下降 |
| 质量 | 事实错误、字幕错误、需求遗漏是否减少 |
| 返工 | 首次交付通过情况、返工次数是否改善 |
| 成本 | 人工、模型和媒体服务的合计成本是否合理 |
| 可控性 | 审批能否被绕过，超限能否停止，版本能否追溯 |

指标分层、三项核心目标和三项底线要求已确认，详见第七题；成本上限、公开发布达成率及完播率目标待定。

当前讨论以视频创作为核心，不以播放量、销量增长作为已经验证的成果。原 MVP 的短视频规格和模拟发布安排，也不能当作真实运营效果。

## 第二题：项目架构

### 1. 架构总体定位

**采用“1 个主管 Agent＋4 个专业子 Agent”的层级架构。**

- DeepAgents：承载主管、子 Agent 及其执行机制，按 LangChain deepagents 框架理解。
- Skills：封装专业 SOP。
- MCP：连接受控工具与数据服务。
- 上下文管理：为每次执行选择必要资料。
- 短中长期记忆：支持任务延续和经验复用。
- 人机交互：承接需求、反馈、预览与审批。
- 多模态：处理文字、图片、音频和视频。
- A2A：本讨论指广义的 Agent 间协作，采用主管—子 Agent 分层结构；拟使用 DeepAgents 内部委派，不以接入 A2A 标准协议为前提。

**固定的是业务目标与强制约束，不是每次调用 Agent 的顺序。**

发布的工具封装与模块归属待设计，不擅自增加运营 Agent 或第五组 MCP。

#### 人物讲解能力如何放入现有架构

继续采用 **5 个 Agent、7 个 Skills、4 组创作 MCP**。在媒体制作能力内明确固定人物参考复用、讲解音频、人物说话与自然动作生成；在审查能力内增加知识表达、人物与声音一致性、口型和自然度检查。不因需要人物出镜新增动作 Agent 或人物 MCP 分组。

**先定义结果要求，再验证技术路线。** “人物参考形象＋讲解音频 → 带自然表情与动作的说话片段”是建议优先验证的路线，不是已经选定的模型或唯一实现方式。是否使用独立口型处理、动作生成或其他组合工具，按实际效果决定；不能把普通视频生成或仅有配音等同于已满足人物讲解能力。

### 3. 五个 Agent 的职责

| Agent | 核心职责 | 主要输出 | 不承担什么 |
|---|---|---|---|
| 主管 | 理解目标、自主编排、委派、验收交付、处理异常 | 计划、子任务、进度与交付说明 | 不替人审批，不擅自追加预算 |
| 资料 | 整理输入、检索补充、核对依据、标记冲突 | 可信事实包、来源、待确认项 | 不编造缺失信息 |
| 脚本 | 编写视频文案、设计镜头、根据意见改稿 | 文案、镜头表、事实引用 | 不擅自增加无依据卖点 |
| 媒体 | 制定制作方案、调用工具制作、局部修复 | 制作清单、成片、制作记录 | 不擅改批准脚本的核心内容 |
| 审查 | 检查脚本与成片，定位问题并提出建议 | 审查报告、问题证据 | 不代替人工审批，不直接改写被审产物 |

“1 个主管”是逻辑角色。不同任务应有隔离的会话与状态，不能让所有项目共用一段混杂的上下文。运营 Agent 不纳入已确认的五个角色。

### 4. 主管怎样自主编排？

主管根据目标、已有资料、执行结果和审查问题，决定下一步。

- 资料充分：不必额外搜索。
- 发现关键事实缺失：派资料 Agent 补证，或询问用户。
- 文案表达不清：派脚本 Agent 修改。
- 字幕不同步：派媒体 Agent 修复。
- 条件不满足或预算耗尽：暂停并请求人工。

**自主权只在允许范围内生效。** 主管可以选择“交给谁处理”，不能自行认定“审批可以跳过”“额度可以重置”。

资料、脚本、成片之间存在产物依赖，但不要求主管机械地调用固定列表。可并行的任务必须没有未满足的依赖。不允许子 Agent 自由互相派活或无限递归委派。

### 5. 七个 Skills

| Skill | 所属 Agent | 对应的专业工作 |
|---|---|---|
| 创作需求澄清 | 主管 | 将模糊需求整理成可执行创作目标 |
| 资料整理与事实核查 | 资料 | 提取事实、核对依据、处理缺口与冲突 |
| 视频文案与镜头设计 | 脚本 | 编写文案，安排画面、旁白与屏幕文字 |
| 媒体制作方案设计 | 媒体 | 选择具体素材，安排配音、字幕和制作参数 |
| 视频合成与局部修复 | 媒体 | 调用工具制作成片，修复指定问题 |
| 脚本审查 | 审查 | 检查依据、需求符合度、表达和可制作性 |
| 成片审查 | 审查 | 对照批准脚本检查视听内容和技术结果 |

每个 Skill 明确：**触发条件、必要输入、操作步骤、输出、完成标准和异常交接方式。**

三种场景共用这些 Skills，按需引用不同规则与模板。主管的基本调度职责写入角色指令；权限、审批和额度由程序控制，不只依赖 Skill 提醒。

制作方案不能擅自改变脚本的核心表达；生成方自检、审查 Agent 检查和人工审批是不同职责，不能相互替代。

### 6. 四组 MCP：一组专属，三组共享

| MCP 服务 | 能力 | 授权使用者 |
|---|---|---|
| 资料检索 MCP | 搜索来源、读取外部资料 | 资料、审查 |
| 项目资料与素材 MCP | 读取需求、事实包、脚本、品牌资料和素材信息 | 五个 Agent 按权限访问 |
| 媒体检测 MCP | 检查参数、抽帧、转写音频、识别画面文字 | 媒体、审查 |
| 媒体制作 MCP | 图片/视频片段生成、配音、字幕对齐、渲染、状态查询、局部重制 | 媒体 Agent 专属 |

通俗理解：

- 资料检索 MCP 是“查资料工具”，去外部寻找信息。
- 项目资料与素材 MCP 是“项目文件室”，读取内部已保存的资料与素材。
- 媒体检测 MCP 是“检查工具箱”，提供参数与视听证据。
- 媒体制作 MCP 是“制作设备”，实际产出或修复视频。

**共享服务，不等于共享全部权限。** 同一服务可以给不同 Agent 开放不同工具，资料访问还要受项目和任务范围限制。工具执行层应校验授权，不能信任 Agent 自填的项目编号。

**专属授权，不等于专属服务器。** 媒体制作只允许媒体 Agent 调用，不要求因此单独购买或部署机器。主管通过任务记录及媒体 Agent 汇报了解进度，不直接发起制作。

AI 图片和视频片段生成已纳入目标能力，扩展现有媒体 Skills 与专属媒体制作 MCP，保持 5 个 Agent、7 个 Skills、4 组创作 MCP。具体供应商和参数待选。双发布方式已确认，但发布封装为内部接口还是 MCP 尚待设计，不能宣称发布工具已接入。

### 7. 上下文管理与记忆

#### 7.1 上下文管理：决定当前该看什么

主管保留用户目标与约束、全局计划和进度、子任务结果摘要及待确认问题。

子 Agent 只接收完成局部任务所需的资料、Skill 和产物引用，不默认复制所有历史对话。大文件通过资产引用按需读取，避免把所有图片、视频和日志塞进主管上下文。

#### 7.2 记忆：决定什么值得继续保留

三层记忆存储与管理原则已确认：短期 Redis；中期 PostgreSQL 项目记录；长期原文保存在 PostgreSQL，经 Embedding 后在 Milvus 中建立向量检索。写入、读取、冲突与清理规则见第三题；具体保留期限、模型和部署参数仍待细化。

| 类型 | 保存内容 | 用途 |
|---|---|---|
| 短期记忆 | 当前执行状态、局部计划、最近结果 | 完成本次任务 |
| 中期记忆 | 项目需求摘要、修改结论、未完成事项 | 跨会话继续同一项目 |
| 长期记忆 | 经确认的品牌规范、稳定偏好、可复用经验 | 支持后续项目 |

**记忆负责保留，上下文管理负责选取。** 正式审批不能只保存在一段记忆摘要里，必须以业务记录为准。上下文隔离不自动等于数据权限隔离。

### 8. 人机交互、多模态与 A2A

#### 8.1 人机交互

用户通过工作台提出需求、补充资料、查看进度、预览脚本和视频，并批准、驳回或提出修改。用户本人具有审核权限，成片按“提交成片预览 → 人工审批 → 确认最终交付”处理；正式记录绑定实际预览的产物版本。

当系统信息不足或超限时，主管应给出：**当前产物、具体问题、已尝试操作、剩余额度和需要人决定的事项。**

#### 8.2 多模态

多模态贯穿整个任务：

- 输入：文档、图片、音频和视频素材。
- 创作：文案与镜头设计。
- 制作：固定虚构人物说话与自然动作、按需图片或片段生成、讲解音频、字幕与画面合成。
- 检查：图像、字幕、旁白与脚本的一致性。
- 交付：可预览的视频成片。

具体能力取决于后续选择的模型和工具，不应把未接入能力写成已经具备。检测应记录覆盖范围和不确定项，抽查若干帧不等于证明全部视频无误。

#### 8.3 A2A

**主管到框架内部子 Agent 的委派，不自动等于 A2A 协议通信。**

本项目按广义 A2A 梳理主管与四个专业子 Agent 的协作，目标采用 DeepAgents 内部委派。A2A 标准协议是另一层技术选型，不因存在多个 Agent 就视为已接入，也不要求为了完整性将 Agent 拆成远程服务。具体职责与交接见第四题。

### 9. 返工、重试与人工接管

采用已确认的限制：

| 项目 | 上限 |
|---|---|
| 资料补充返工 | 初次提交后，最多自动补充 1 轮 |
| 脚本返工 | 初稿后，最多自动修改 1 轮 |
| 图片素材返工 | 每个需生成图片的镜头首次 3 个候选；本任务图片阶段最多修改 1 轮 |
| 视频片段返工 | 每个需生成片段的镜头首次 1 个候选；本任务片段阶段最多修改 1 轮 |
| 成片合成返工 | 首次 1 条完整视频；本任务合成阶段最多修复 1 轮 |
| 技术失败重试 | 同一操作首次失败后，最多额外重试 2 次 |
| 全任务自动返工 | 各阶段累计最多 4 轮 |

- 计数不能因重新委派、换版本或暂停恢复而清零。
- 跨阶段返回也要检查该阶段剩余额度。
- 人工意见触发的自动修改同样计入返工。
- 技术故障与内容返工分别计数，不能互相替代。
- 各执行层不得叠加隐藏重试；结果不明时先核对原操作，避免重复提交和扣费。
- 权限缺失、无效参数等不可机械重试。

**最新规则为资料、脚本、图片、视频片段、成片合成五阶段各最多 1 轮自动返工，阶段额度合计 5 轮，但全任务总上限仍为 4 轮，以先触及的限制为准。**

媒体额度不再是所有环节共用一轮，也不是每个镜头各一轮。阶段汇总问题集中处理算一轮，不得把后续新问题不断并入同一轮绕过额度。图片修改选中候选；三个都不合格时，每个受影响镜头生成 1 个修正版，不重新出 3 个。片段和成片只修受影响部分，修改后仍不合格即转人工。

超限后暂停并转人工，主管不能自行增加额度。读取 Skill 不等于执行一轮返工，计数应绑定正式接受的返工操作。

### 10. 与代码实现的关系

本节描述讨论时的核对结果和目标差距，不对之后的工作区变更作实现验收。

| 状态 | 内容 |
|---|---|
| 此前核对的代码基础 | 业务 API、任务与内容版本记录、审批与审计、本地工作流、局部媒体适配器 |
| 本次确定的设计基线 | 主管式自主编排、5 个 Agent、7 个 Skills、4 组 MCP、受控返工与重试 |
| 仍需细化或实施 | DeepAgents 接入、工具实现、上下文与记忆存储、工作台与 Agent 集成、A2A 边界及完整执行集成 |

未来集成时应保持：

> DeepAgents 决定下一步尝试什么；受控执行层和业务系统决定该动作是否被允许，并保存正式结果。

现有工作流不能直接当作已具备自主编排能力，需要明确触发、授权和执行边界，避免主管与工作流重复启动同一项制作。

## 第三题：数据流怎么画、怎么讲？

### 1. 什么是数据流？

大白话：**资料从哪里来、谁使用、做完交出什么、保存在哪里，最后怎样到用户手中。**

数据流不是固定调用路线。主管可自主选择子 Agent、补资料或向用户询问，但需求、事实、脚本、成片和审批之间的依赖必须明确。下图表示主要产物依赖，不要求主管机械执行一串调用。

### 2. 主干数据流图

```text
用户提出需求，上传文档 / 图片 / 音频 / 视频
                       ↓
原始输入保存：文件 + 来源 + 所属项目 / 任务
                       ↓
主管 Agent → 创作需求单
目标、场景、时长、风格、约束、资料引用、待确认项
                       ↓
资料 Agent → 事实与证据包
可用事实、来源位置、冲突项、不确定项、素材使用限制
                       ↓
脚本 Agent → 视频文案与镜头表
人物台词、时间段、出镜与辅助画面、屏幕文字、知识引用
                       ↓
审查 Agent → 脚本审查报告
问题位置、依据、修改建议、未覆盖与不确定内容
                       ↓
向用户提交脚本与检查结果 → 人工审批脚本版本
             ├─ 要求修改 → 主管检查额度并组织处理
             └─ 满足审批条件
                       ↓
媒体 Agent → 制作清单
批准脚本、固定人物参考、声音设定、素材与输出要求
                       ↓
准备并关联人物参考版本、台词音频版本
人物首次建立与跨视频复用分别记录，不每个镜头随意换人
                       ↓
专属媒体制作 MCP → 工具执行
制作人物说话与自然动作片段；按需制作辅助画面
候选初筛与审查 → 保存音频 / 人物片段 / 字幕 / 渲染关联
                       ↓
成片版本与资产引用
                       ↓
审查 Agent + 媒体检测 MCP → 成片审查报告
知识与台词、口型、人物与声音一致性、自然动作、参数及覆盖范围
                       ↓
主管提交成片预览
可播放视频 + 版本 + 关联脚本 + 检查报告 + 关注事项
                       ↓
用户本人观看并审批
             ├─ 驳回 / 要求修改
             │       ↓
             │   主管检查问题归属与剩余额度
             │       ├─ 有额度 → 修复、复查、重新提交预览
             │       └─ 无额度 → 暂停并转人工
             │
             └─ 批准且满足适用审批条件
                       ↓
正式记录绑定视频版本与关联脚本版本
                       ↓
业务系统确认最终交付 → 主管通知用户
交付同一已批准视频，不重新生成，不因交付直接触发发布
                       ↓ 用户选择发布方式
       ├─ 手动：下载 → 自行上传 → 回填链接并核实
       └─ 代发：选择授权账号 → 预览设置 → 单独确认发布
                                      ↓
                          保存回执并跟踪公开结果
```

机器审查与人工审批是两类数据：前者记录检查结论，后者记录有权限用户的正式决定。模型不能凭“没发现问题”替用户批准。

### 3. 用一条人物知识讲解任务解释

示例请求：“根据我提供的知识资料，让固定虚构讲解者用通俗语言讲清一个知识点，自然点头和做手势，不编造结论。”这是流程示例，不指定实际知识领域、视频时长或已完成的制作任务。

| 阶段 | 收到什么 | 处理后交出什么 | 关键边界 |
|---|---|---|---|
| 接收输入 | 用户要求、知识资料、已有的人物参考 | 原始输入记录、文件引用 | 原件保留，摘要不能替代原始依据 |
| 澄清需求 | 原始要求、现有资料 | 创作需求单 | 明确区分用户要求与模型推断 |
| 整理事实 | 需求单、文档与外部资料 | 事实与证据包 | 每项关键事实关联来源，冲突不隐藏 |
| 创作文案 | 需求单、知识依据、人物设定引用与素材信息 | 口语化台词与镜头表 | 不为简化表达而改变知识含义 |
| 审核脚本 | 脚本、依据、用户要求 | 检查报告、正式审批记录 | 机器检查和人工批准分开保存 |
| 制作视频 | 有效批准脚本、人物参考、声音设定与素材 | 制作清单、台词音频、人物说话片段及成片 | 不擅改台词，绑定人物与音频版本，素材先筛查再使用 |
| 检查成片 | 成片、批准脚本、检测证据 | 带位置的成片审查报告 | 说明检查范围，不声称抽帧覆盖全部画面 |
| 预览与审批 | 视频、版本、审查报告 | 用户决定和意见 | 批准必须对应实际查看的版本 |
| 最终交付 | 有效成片与正式审批状态 | 视频引用、版本、审核状态、必要说明 | 可以在同一页面更新状态，无须再生成视频 |
| 发布 | 批准成片、用户所选方式；代发需账号授权与单独发布确认 | 链接、回执、发布状态和核实来源 | 未核实不得标为确认公开 |

镜头表回答“每一段看什么、听什么”；制作清单回答“用哪份素材、声音和参数具体实现”。这两种产物不能混同。

### 4. 已确认的七条交接规则

1. **主管统一派活。** 子 Agent 完成后向主管汇报，不随意互相委派，也不递归扩建团队。
2. **派活附任务单。** 写清做什么、依据什么、有哪些限制、完成后交什么。
3. **相关资料给齐。** 关键约束直接写入任务说明，详细资料通过授权引用读取；不复制整个项目历史，不跨项目越权读取。
4. **先保存结果再汇报。** 返回完成状态、摘要、产物引用和待解决问题；没做完不能说完成，工具成功不等于业务完成。
5. **修改产生新版本。** 保留旧稿、变更原因和输入关联，不悄悄覆盖；主管交接明确的版本。
6. **AI 检查与用户批准分开。** 用户本人有审批权限，但后端仍校验权限、版本及适用条件；未经批准不能标为最终交付。
7. **异常有上限。** 返工与技术重试分别计数，超限暂停并转人工，换版本或重新委派不能清零。

主管交给脚本 Agent 的任务单可以是：

```text
任务：编写固定虚构人物的知识讲解台词与镜头表
范围：当前用户有权限的项目和任务
需求依据：创作需求单 v1
事实依据：事实与证据包 v1
素材：允许使用的人物参考与知识辅助画面引用
约束：表达通俗；不编造知识；动作自然，不要求精确指向
交付：文案、镜头表、事实引用、待确认项
```

脚本 Agent 返回的结果可以是：

```text
状态：完成 / 部分完成 / 需要补充信息
摘要：采用了什么表达方式
产物：已保存的脚本版本引用
依据：使用了哪些资料版本
问题：尚未解决的事项与原因
```

这些字段是便于理解的交接示例，尚不是已经实现的接口契约。文件引用可以是内部资产编号，并不要求生成公开链接；读取时仍需检查权限。

#### 人物、音频与视频的交接补充

每段人物视频要能够追溯到任务和镜头、批准脚本、人物参考、声音设定以及实际台词音频的版本。文件本体存入文件仓库，引用、归属和版本关系进入正式项目记录，交接时不复制整段视频到上下文。

- 台词变化后，检查对应音频、人物片段、字幕及成片是否需要重新制作；不能只改字幕却保留旧话音。
- 音频变化后，重新检查人物片段与新音频的口型、时序和时长关系，不能自动沿用旧审查结论。
- 人物参考或声音设定变化后，标明受影响产物及版本；新成片仍需重新预览审批。
- 人物首次建立和之后复用分开处理。固定人物不是每个镜头重新任选一个人，也不意味着所有服装与背景必须永久不变。

**建议增加人物设定与参考素材记录：**保存人物标识、外观方向、参考素材、声音设定、适用账号或项目范围与版本。它属于现有项目记录与素材管理，不是新增 Agent 或数据库。具体字段、人物预览是否需要独立审批及批准失效规则仍待设计，不在本轮擅自增加审批关卡。

可复用且已确认的人物要求按现有长期记忆规则管理；具体文件引用、版本和正式审批仍以业务记录为准。不能仅凭记忆摘要选择人物，也不能跨账号或项目越权复用。

### 5. 数据存在哪里？

按完整目标架构划分，不把所有信息混进一个记忆库。

```text
工作台 / 主管 / 子 Agent
            ↓ 经受控接口按权限访问
┌───────────┬──────────────────────┬────────────┬────────────┐
│ Redis     │ PostgreSQL           │ Milvus     │ 文件仓库   │
│ 短期记忆  │ 中期项目记忆         │ 长期向量   │ 原始文档   │
│ 执行存档  │ 长期原文与有效状态   │ 检索关联   │ 图片/音频  │
│ 等待状态  │ 任务、版本、审批额度 │ 信息       │ 字幕/视频  │
└───────────┴──────────────────────┴────────────┴────────────┘
```

| 存储 | 保存内容 | 不承担的职责 |
|---|---|---|
| Redis | 当前会话、计划、执行检查点、必要结果引用、等待状态 | 不作为正式审批和返工额度的唯一依据 |
| PostgreSQL | 项目记忆、长期记忆原文及元数据、任务与版本、正式审批、执行计数 | 不能把 AI 摘要当作正式审核决定 |
| Milvus | 长期记忆向量、原文记录标识、检索与过滤所需关联信息 | 不替代原文，也不把相似度当成可信度或授权 |
| 文件仓库 | 原始文档、图片、音频、字幕、视频和其他文件 | 不独自决定文件是否已批准或可跨项目使用 |

数据库保存文件归属、版本与引用，文件仓库保存文件本身。文件仓库具体技术、Embedding 模型、索引和部署参数仍需后续选型；不默认用 pgvector 替代已确认的 Milvus。

### 6. 三层记忆分别保存什么？

| 记忆层 | 技术方向 | 内容 | 大白话 |
|---|---|---|---|
| 短期 | Redis | 当前任务对话、计划、执行进展、暂停恢复所需状态 | 这次工作做到哪里了 |
| 中期 | PostgreSQL 项目记录 | 项目需求、方案取舍、修改结论、未完成事项、产物引用 | 这个项目已经决定过什么 |
| 长期 | PostgreSQL 原文 + Embedding + Milvus 向量检索 | 确认过的品牌规范、稳定偏好、可复用知识与经验 | 以后做类似事情值得参考什么 |

中期记忆是项目级工作笔记；长期记忆用于跨任务复用。它们不会仅因时间过去就自动升级或搬迁。是否保留取决于信息价值、适用范围及确认状态。

短期不是随时可丢的缓存：需配置持久化、恢复与容量策略，等待用户审核期间不能因随意设置的过期时间丢失执行存档。检查点恢复也不能导致重复渲染或重复扣费。

### 7. 记忆写入规则

| 信息来源与范围 | 写入处理 | 示例 |
|---|---|---|
| 用户明确要求长期记住 | 保存并反馈内容与适用范围，不重复询问同一明确指令 | “以后品牌 A 的字幕默认白色” |
| Agent 自己提炼的经验 | 先作为候选，用户确认后才进入有效长期记忆 | “用户似乎更喜欢简短文案” |
| 仅限当前任务的信息 | 保留在短期或中期，不自动上升为长期规则 | “这条视频不要出现价格” |

长期写入流程：

```text
发现可复用信息
      ↓
判断范围、来源与是否已经明确确认
      ↓ 必要时请用户确认
PostgreSQL 保存正式原文、来源、版本、范围和确认状态
      ↓
Embedding 模型生成向量
      ↓
Milvus 保存向量和原文关联
      ↓
记录检索同步状态并向用户反馈
```

原文已保存与向量已同步是不同状态，不能在同步失败时宣称记忆已经完整可检索；具体同步和补偿机制在实施设计中确定。

### 8. 记忆读取规则与上下文管理

**先限定权限和范围，再选取相关内容。**

```text
确定当前用户、项目、品牌和任务
            ↓
读取本项目有效的需求与修改结论
            ↓
明确读取必须遵守的品牌规则
            ↓
按权限和范围通过 Milvus 检索参考经验
            ↓
回查 PostgreSQL 原文、确认状态、版本与有效性
            ↓
上下文管理裁剪、整理必要内容
            ↓
交给需要这些内容的 Agent
```

- 强制规则直接读取，不能依赖语义检索碰巧命中。
- 参考经验用向量搜索查找，相似不等于正确，也不代表必须照做。
- 读取结果需要核对权限、项目或品牌范围、确认状态和有效性；Agent 自填范围不能代替授权。
- 主管保留目标、全局进度和摘要；各子 Agent 只读取职责相关内容，不复制所有聊天、工具日志和文件。
- 来源原文及引用仍然保留，摘要不能替代全部依据。

| Agent | 主要需要的上下文与记忆 |
|---|---|
| 主管 | 项目目标、关键决定、当前进度、待解决问题 |
| 资料 | 已有事实、来源、资料缺口、用户确认结论 |
| 脚本 | 品牌表达要求、禁用表述、文案偏好、事实依据 |
| 媒体 | 批准脚本、字幕风格、声音偏好、制作要求 |
| 审查 | 用户要求、适用规范、被审与批准版本、历史问题 |

正式审批从业务记录读取，不能以“记忆里说用户批准过”作为执行依据。

### 9. 记忆冲突、更新与删除

#### 9.1 新旧要求冲突

- “这条用黄色字幕”：只改当前任务，不修改默认白色的长期偏好。
- “以后都用黄色字幕”：更新该品牌长期记录，让旧偏好失效，同步向量检索。
- “换黄色吧”：范围不清楚时询问是只改本次，还是以后都改。
- 新要求与强制规范冲突：暂停相关操作，说明冲突，由有权限的人处理；Agent 不自行绕过。

历史经验不能擅自覆盖当前明确要求；当前要求也不能自动绕过权限、审批或强制规范。

#### 9.2 保留、归档与清理

| 类型 | 已确认的原则 |
|---|---|
| 短期 Redis | 任务执行、等待审批或等待人工处理时保留；结束且必要记录完整保存后，按策略清理 |
| 中期 PostgreSQL | 项目结束后归档，不立即删除；后续按约定保留期限清理 |
| 长期记忆 | 有效期间保留；过期、被替代或用户要求删除时停止使用 |

失效与删除需要区分：旧偏好失效后可按策略保留变更历史，但不得继续提供给 Agent。用户要求删除时，需要处理 PostgreSQL 原文、Milvus 向量和相关缓存；备份按备份保留策略清理。

若删除或索引同步失败，先把正式记录标为不可使用；即使旧向量仍被检索命中，也不能进入 Agent 上下文。具体保留天数与恢复目标尚未确定，不编造数值。

### 10. 版本、审批与异常数据如何流转？

| 情况 | 数据处理 | 后续动作 |
|---|---|---|
| 脚本 v1 改为 v2 | 保留 v1、新增 v2、记录修改原因和依据 | 重新检查与审批，不能拿 v1 的批准制作 v2 |
| 成片 v1 改为 v2 | 保存新旧成片，关联输入和修复记录 | 新版重新预览审批，不能直接继承旧版批准 |
| 成片暴露脚本事实错误 | 回查事实包及脚本，标记受影响产物 | 检查上游返工额度，超限转人工 |
| 制作操作超时 | 保留操作编号、尝试次数及结果未知状态 | 先查询原任务，防止重复执行 |
| 返工额度耗尽 | 保存现有产物、错误和累计次数 | 暂停，交付人工处理说明，不自动清零 |
| 用户批准视频 | 记录用户、时间、决定、意见、视频和脚本版本 | 核对正式状态后确认交付同一版本 |

用户本人具有审核权限，不表示后端可以省略授权和版本校验；若适用策略要求更多审批条件，也不能由 Agent 擅自降低。

### 11. 数据流总结

> 用户资料先保存，主管明确目标；资料、脚本、媒体和审查 Agent 交接有依据、有版本的产物。用户先预览成片再审批，系统记录正式决定后交付同一视频。项目过程沉淀在 PostgreSQL，执行存档保存在 Redis，经确认的长期知识以 PostgreSQL 原文和 Milvus 向量支持检索。上下文只选取当前有权使用且相关的信息，失效记忆不再参与创作。交付后由用户选择手动发布或单独确认系统代发，发布状态与效果数据另行核实记录。

## 第四题：A2A 结构与 Agent 职责

### 1. 这里的 A2A 是什么意思？

本题的 A2A 使用广义含义：**Agent 之间分工、交接与协作**。项目采用主管—子 Agent 的分层结构，也可描述为 Supervisor / Hierarchical 协作模式。

必须区分：

| 概念 | 本项目的表述 |
|---|---|
| 多 Agent 协作结构 | 一个主管协调资料、脚本、媒体和审查四个专业角色 |
| 内部委派方式 | 目标使用 DeepAgents 内部任务委派与结果回传机制 |
| A2A 标准通信协议 | 是独立技术选型，当前设计不以接入该协议为前提 |
| 部署方式 | 不因为有多个 Agent 就要求拆成多台机器或远程服务 |

不能说“内部子 Agent 不属于多 Agent 协作”，也不能仅因有主管和子 Agent 就宣称“已经接入 A2A 标准协议”。完整目标架构不等于必须远程拆分所有角色。

### 2. 分层协作结构图

```text
                           用户
                            ↕
               需求 / 反馈 / 预览 / 正式审批
                            ↕
                       主管 Agent
             理解 → 规划 → 委派 → 验收 → 汇报
                            │
          ┌───────────┬─────┴─────┬───────────┐
          ↕           ↕           ↕           ↕
       资料 Agent   脚本 Agent   媒体 Agent   审查 Agent
       事实与来源   文案与镜头   制作与修复   脚本/成片检查
          │           │           │           │
          └───────────┴─────┬─────┴───────────┘
                            ↓
          角色指令 + 专业 Skills + 获准 MCP 工具
                            ↕
       上下文 / 三层记忆 / 文件资产 / 正式业务记录

约束：权限、版本、审批、返工与重试额度由程序校验。
交接：子 Agent 向主管返回结果，不自由互相派活。
```

每个任务具有隔离的会话与执行状态；“一个主管”是角色定义，不是全公司共享一个上下文。五个角色不等于五台服务器，也不要求每次把四个子 Agent 全部调用一遍。

### 3. 职责数量总览

以下数量是对职责的分组，不是模型调用次数或必须执行的步骤数。

| Agent | 主要职责数量 | 一句话定位 | 对应 Skills |
|---|---|---|---|
| 主管 | 6 类 | 组织工作，不包办专业工作 | 创作需求澄清 |
| 资料 | 3 类 | 整理事实、依据与缺口 | 资料整理与事实核查 |
| 脚本 | 3 类 | 决定视频说什么、每段展示什么 | 视频文案与镜头设计 |
| 媒体 | 3 类 | 把批准方案制作成视频 | 媒体制作方案设计；视频合成与局部修复 |
| 审查 | 2 类 | 独立检查脚本与成片 | 脚本审查；成片审查 |

运营 Agent 不纳入已确认的五个角色。系统代发是单独受控业务能力，由用户单独确认后执行；工具封装与模块归属待设计，不默认允许任何 Agent 自由发帖。

### 4. 主管 Agent：六类职责

1. **理解需求：**明确目标、场景、时长、风格和约束，必要时向用户询问。
2. **规划任务：**判断当前缺什么、需要哪些专业工作以及依赖关系。
3. **分配工作：**选择子 Agent，提供任务单、必要资料和完成要求。
4. **验收交付：**检查返回内容是否完整、问题是否解决，是否需要独立审查。
5. **处理异常：**组织补证、改稿和恢复，超限或无法判断时转人工。
6. **统一汇报：**展示进度，提交脚本和成片预览，正式批准后通知交付。

- 输入：用户需求、任务状态、子 Agent 结果、用户反馈。
- 输出：创作需求单、任务安排、处理决定、进度和交付说明。
- MCP 范围：按权限读取项目资料与产物信息；委派、业务状态和人工交互采用内部受控机制。
- 不负责：代替人审批、自行增加额度、直接绕过媒体 Agent 发起制作、任意修改正式业务状态。

主管验收是检查子任务交付是否满足要求，不意味着把专业审查再做一遍，也不能替代人工批准。

### 5. 资料 Agent：三类职责

1. 阅读用户提供的文档、图片说明和其他资料。
2. 按需要检索补充、核对来源和信息冲突。
3. 整理可用事实、证据位置、素材限制与待确认内容。

- 输入：需求单、原始资料、允许访问的来源。
- 输出：事实与证据包。
- MCP 范围：共享资料检索、共享项目资料与素材。
- 不负责：编造缺失信息、将搜索命中当作自动证实、擅自批准内容。

示例：“这个知识结论有原始资料支持，但只在特定条件下成立；另一个说法没有证据，需要确认后才能引用。”

### 6. 脚本 Agent：三类职责

1. 根据需求与事实确定表达角度。
2. 编写视频文案与镜头表，关联事实依据和素材需求。
3. 根据审查或用户意见，在额度内修改。

- 输入：需求单、事实包、品牌要求、素材信息。
- 输出：文案、镜头表、依据引用和待确认项。
- MCP 范围：按权限使用项目资料与素材；写作本身由模型完成，不强求独占工具服务。
- 不负责：添加无依据卖点、直接制作视频、把新稿视为已获批准。

镜头表说明每个时间段展示什么、人物或旁白说什么、屏幕出现什么文字；不要求每次绘制图像分镜。

### 7. 媒体 Agent：三类职责

1. 根据批准脚本选择用户素材、授权素材或 AI 生成方式，制定素材、配音、字幕和镜头清单。
2. 调用工具生成候选图片或片段，初筛后提交审查；制作中间资产和成片，保存结果。
3. 根据问题报告在额度内局部修复并自检。

- 输入：有效批准脚本版本、素材和输出要求。
- 输出：制作清单、配音与字幕等中间产物、成片、制作记录。
- MCP 范围：专属媒体制作；共享项目资料与素材、媒体检测。
- 不负责：擅改批准脚本核心表达、绕过审批、超额重制、代替审查 Agent 或用户批准。

素材不足或镜头无法实现时返回主管，不悄悄换成改变含义的画面。主管通过任务记录和汇报了解制作，不与媒体 Agent 同时发起重复渲染。

### 8. 审查 Agent：两类职责

1. **脚本审查：**核对事实依据、需求符合度、表达以及镜头可制作性。
2. **成片与制作素材审查：**沿用成片审查 Skill，检查候选素材的事实和画面要求，再对照批准脚本检查成片、声音、字幕和技术结果，不另增第八个 Skill。

- 输入：被审版本、需求和依据、适用规范、检测证据。
- 输出：问题清单、位置、证据、修改建议、覆盖范围和不确定项。
- MCP 范围：共享检索、项目资料与素材、媒体检测。
- 不负责：直接修改被审产物、代替用户批准、把“未发现问题”当作绝对正确。

示例：“第 6 秒的字幕与旁白不一致，建议媒体 Agent 修复。”检测工具提供证据，审查 Agent 负责按要求判断；媒体自检不替代独立审查。

#### 知识讲解场景的职责补充

| 角色 | 本轮补充职责 | 边界 |
|---|---|---|
| 主管 Agent | 保持知识讲解目标，协调固定人物、声音和制作问题 | 不因人物表现要求增加角色或绕过审批 |
| 资料 Agent | 核查知识依据、适用条件和不确定项，整理参考资料来源 | 不把人物形象或生成画面当作知识证据 |
| 脚本 Agent | 把知识讲清楚，编写适合口述的台词、例子、节奏与镜头 | 通俗化不能篡改含义，不默认写商品操作步骤 |
| 媒体 Agent | 复用人物参考，准备讲解音频，制作自然说话与动作及辅助画面 | 不要求逐个手势精准编排；具体模型和技术组合待验证 |
| 审查 Agent | 检查知识、台词、口型、跨片人物与声音一致性和动作自然度 | 无可靠检测证据时标明不确定并转人工，不假定工具已接入 |

原有主管六类、资料三类、脚本三类、媒体三类、审查两类的职责分组不变；以上是场景内的具体要求。

### 9. 谁决定调用谁？

| 当前情况 | 主管的处理方向 |
|---|---|
| 资料充分 | 不为完成形式而强行联网搜索 |
| 缺少事实依据 | 派资料 Agent 补证，或向用户询问 |
| 需要文案与镜头设计 | 派脚本 Agent |
| 脚本满足审批条件，需要制作 | 经业务校验后派媒体 Agent |
| 需要检查脚本或成片 | 派审查 Agent |
| 字幕有问题 | 派媒体 Agent 局部修复，不无条件重跑全部上游 |
| 信息冲突或额度耗尽 | 暂停相关动作，向用户交接问题 |

只有无未满足依赖的任务才可并行。自由选择下一步不等于自由更改审批、权限或预算。

### 10. Agent、Skills、MCP、业务控制怎样分工？

| 部分 | 负责什么 | 大白话 |
|---|---|---|
| Agent | 结合目标和状态作专业判断并执行任务 | 谁负责干活 |
| Skills | 可复用 SOP、输入输出要求、异常处理方法 | 应该怎么干 |
| MCP 工具 | 读取资料或调用具体外部能力 | 用什么工具干 |
| 上下文与记忆 | 提供相关、有效且有权限的信息 | 干活时需要知道什么 |
| 业务控制 | 校验权限、版本、审批和执行预算 | 现在允不允许干 |
| 用户 | 提供信息、纠正方向、审批关键产物 | 谁作最终确认 |

DeepAgents 内部运行与业务 Workflow 不争夺同一项制作的触发权：主管提出执行意图，受控入口校验条件后才授权执行。正式状态由业务记录确认，不由模型一句“已完成”直接决定。

### 11. 异常、人工协作与场景复用

- 使用第三题的版本化任务单和结果交接规则，子 Agent 做完回主管。
- 使用第二题最新规则：资料、脚本、图片、片段、成片合成五阶段各最多 1 轮返工，同一操作额外最多 2 次技术重试，全任务返工最多 4 轮，以先触及的限制为准。
- 超限后带着产物、问题、原因和已尝试操作转人工，不能通过换 Agent 或换版本重置。
- 成片先给用户预览，再由有权限的用户审批，最后正式交付同一版本。
- 当前优先使用知识讲解规则；科技资讯、客户交付和商品营销保留为可复用场景，共用五个角色。不同项目、账号与品牌的资料、人物和偏好不能混用。

### 12. 可直接用于介绍项目的表述

> Live Make 采用主管—子 Agent 的分层多智能体协作架构。主管 Agent 负责理解需求、自主规划、任务委派、交付检查和人机沟通；资料、脚本、媒体、审查四个专业 Agent 分别负责事实整理、文案与镜头设计、视频制作和质量检查。
>
> 各 Agent 使用专业 Skills 和获准的 MCP 工具，通过明确的任务说明与版本化产物交接。系统不写死所有调用顺序，但通过程序强制执行审批、权限、返工和重试限制。Agent 间拟采用 DeepAgents 内部委派；本题按广义 A2A 讨论协作结构，不宣称已经接入 A2A 标准协议。

## 第五题：Skills 有哪些？对应人工哪个环节？SOP 怎么走？

### 1. 先理解 Agent、Skill 与 SOP

**Agent 是负责某项工作的角色，Skill 是这个角色可复用的工作方法，SOP 是方法里面的操作步骤。** 比如媒体 Agent 像制作人员，“视频合成与局部修复”像制作手册，MCP 工具则是实际操作的设备。

以下是已确认的 **7 个 Skills 的目标职责与 SOP**，不是“仓库已经安装并验证了七个技能”的实现声明。它们服务同一条从零创作路线；主管按当前缺口选择工作，不代表必须逐条机械调用。

### 2. 对齐人工工作环节

| Skill | 负责人 | 对应人工环节 | 主要产物 | 配合的 MCP |
|---|---|---|---|---|
| 创作需求澄清 | 主管 Agent | 编导与需求方沟通 | 创作需求单 | 项目资料与素材 |
| 资料整理与事实核查 | 资料 Agent | 编辑整理资料、查证 | 事实包、来源和待确认项 | 项目资料与素材、资料检索 |
| 视频文案与镜头设计 | 脚本 Agent | 编剧写文案和分镜 | 有版本的文案与镜头表 | 项目资料与素材 |
| 媒体制作方案设计 | 媒体 Agent | 制片确认素材和制作方式 | 制作清单、素材方案与输出要求 | 项目资料与素材、媒体检测 |
| 视频合成与局部修复 | 媒体 Agent | 美术、配音、剪辑与修片 | 候选素材、配音字幕、视频版本 | 项目资料与素材、媒体制作、媒体检测 |
| 脚本审查 | 审查 Agent | 编辑审稿、核事实与需求 | 绑定脚本版本的审查报告 | 项目资料与素材、资料检索 |
| 成片审查 | 审查 Agent | 审素材、看片质检 | 绑定素材或成片版本的审查报告 | 项目资料与素材、媒体检测；必要时资料检索 |

“分镜”就是把视频拆成一个个镜头，写明**这一段多长、画面是什么、说什么、屏幕显示什么字**；不是要求用户懂拍摄术语，也不意味着所有镜头都需要 AI 生成。

### 3. Skill 一：创作需求澄清

- **何时使用：**收到新需求，或现有需求存在影响制作的关键缺口。
- **输入：**用户描述、上传资料、项目约束、当前有权使用的偏好。
- **SOP：**读取资料 → 明确视频目的与受众 → 梳理时长、风格、必须包含和禁止出现的内容 → 标记缺失或冲突 → 只对关键缺口询问用户 → 形成需求单。
- **输出与完成标准：**可供后续工作的需求单，明确已确认事项、假设、待确认事项和版本；关键限制不能靠 Agent 猜测。
- **异常交接：**目标互相矛盾或关键事实不明时暂停相关工作，由主管询问用户。

用户沟通、任务委派和正式状态更新走受控业务能力，不强行包装成 MCP，也不另增一个“调度 Skill”。

### 4. Skill 二：资料整理与事实核查

- **何时使用：**需要把原始资料变成可信的创作依据。
- **输入：**需求单、用户知识资料、适用规范及必要的检索范围；实际涉及品牌或商品时再加载相应记录。
- **SOP：**优先整理用户资料 → 提取可核对事实 → 绑定原始来源与适用范围 → 检查冲突、时效和缺口 → 必要时外部检索补证 → 区分已证实、存在冲突和未证实内容。
- **输出与完成标准：**事实包、来源引用、可用素材引用、风险和待确认项；关键事实必须能回到依据，检索不到不能编造。
- **异常交接：**补充返工最多 1 轮且受全任务额度限制；仍不足时转人工，不把不确定内容写成确定结论。

### 5. Skill 三：视频文案与镜头设计

- **何时使用：**需求与事实依据足够，准备形成可审核脚本。
- **输入：**有效需求单、事实包、场景规则和可用素材信息。
- **SOP：**明确知识点与依据 → 用通俗语言组织开头、解释、例子和结尾 → 编写适合口述的台词 → 安排停顿、强调与镜头 → 按需加入辅助画面和字幕 → 核对知识含义、时长与可制作性 → 保存脚本版本。自然手势只说明总体表现，不要求逐个定时编排。
- **输出与完成标准：**文案和镜头表相互对应，事实有依据，镜头可执行；这是“待审脚本”，不是已批准制作指令。
- **异常交接：**事实不足交主管组织补证；脚本最多自动修改 1 轮。改变核心表达后必须重新完成相应审查与审批。

### 6. Skill 四：媒体制作方案设计

- **何时使用：**脚本正式批准后，决定怎样把它做出来。
- **输入：**已批准脚本及版本、素材清单、品牌约束、输出规格和剩余额度。
- **SOP：**核对脚本批准状态 → 读取固定人物参考与声音设定 → 检查素材来源、版本与权限 → 安排人物出镜和按需辅助画面 → 明确台词音频、自然动作、字幕与合成要求 → 形成可执行制作清单。人物首次建立与后续复用分开安排，具体技术路线待验证。
- **输出与完成标准：**每个镜头有明确素材来源或生成计划，实际输出规格明确；不得用“制作优化”偷偷改变已批准脚本。
- **异常交接：**人物参考、知识辅助素材、必要授权或其他关键输入缺失时报告主管；涉及商品时同样检查真实素材。预算与能力不够时先说明，不能承诺工具做不到的效果。

### 7. Skill 五：视频合成与局部修复

- **何时使用：**制作方案具备执行条件，或收到明确定位的媒体问题。
- **输入：**有效批准脚本、制作清单、素材引用、审查意见和阶段预算。
- **SOP：**校验版本与额度 → 获取或建立人物参考，准备批准台词对应的音频 → 制作人物说话与自然动作片段及所需辅助素材 → 媒体 Agent 初筛并提交审查 → 制作字幕并合成 → 查询并核实结果 → 自检并保存关联版本 → 必要时局部修复。此处描述交接依赖，具体模型内部处理顺序不作预设。
- **输出与完成标准：**可预览的实际媒体文件、版本、关联脚本、素材来源和执行记录；工具返回“受理”不算完成。
- **异常交接：**生成数量、阶段返工、全任务额度和技术重试按第六题执行；结果未知先查询，仍不合格或超限转人工。

图片与片段生成纳入这两个媒体 Skills，不为了新增工具就新增 Agent 或拆出一批重复 Skills。

### 8. Skill 六：脚本审查

- **何时使用：**脚本初稿或修订稿完成，需要独立检查。
- **输入：**待审脚本具体版本、需求单、事实包和适用约束。
- **SOP：**锁定被审版本 → 对照需求 → 核查关键事实与表达 → 检查品牌约束、时长和可制作性 → 标注问题位置、依据及修改建议 → 返回审查报告。
- **输出与完成标准：**结论、问题清单、证据与未覆盖事项明确；不能只返回一个没有解释的分数。
- **异常交接：**证据不足要标为不确定，交主管补证或询问用户；报告通过不等于人工批准。

### 9. Skill 七：成片审查

- **何时使用：**需要检查生成素材候选、修订素材或完整视频。
- **输入：**明确版本的素材或成片、批准脚本、知识依据、人物参考与声音设定、适用规范、输出规格和历史问题。
- **SOP：**核对版本关联 → 读取实际媒体参数 → 根据需求抽帧、转写与识别文字 → 核对知识与台词 → 检查口型、人物和声音一致性、表情手势及辅助画面 → 复查历史问题 → 输出定位到镜头或时间点的报告。不能从普通抽帧或转写结果直接推断口型与自然度全部合格；检测不足处明确交人工。
- **输出与完成标准：**有实际证据、检查覆盖范围、问题和不确定项；抽查部分画面不能宣称全片每一帧都正确。
- **异常交接：**工具检测不到、真实性存疑或判断存在争议时转人工；修改后复查新版本，不能沿用旧版结论。

生成候选的独立检查复用此 Skill，不另增“候选审核 Skill”。最后仍遵守：**提交成片预览 → 人工审批 → 确认最终交付**。

### 10. 为什么保留七个，而不是越多越好？

这七个覆盖需求、资料、脚本、制作方案、实际制作和两类审查，边界对应人工分工。当前补入知识通俗化、固定人物复用与人物说话制作；科技资讯、客户内容交付、商品营销保留规则模板，不另建一套 Agent 与 Skills。

每个 Skill 后续实现时都应带必要输入、SOP、输出结构、完成标准和异常出口。权限、版本、审批及额度是程序强制执行的约束；写进工作手册可以提醒，但不能替代后端校验。

## 第六题：MCP 有哪些？对应人工哪个环节？工具干什么用？

### 1. 一组专属，加三组共享

**Skill 告诉 Agent 怎么做；MCP 提供调用具体工具的接口。** 本项目按业务用途规划四组创作 MCP，组数不是工具数量，也不等于服务器数量。以下是目标能力清单，不是已安装服务、已接入供应商或已验证接口的声明。

| MCP 分组 | 人工对应环节 | 主要能力 | 授权边界 |
|---|---|---|---|
| 资料检索 MCP，共享 | 上网查资料、核对出处 | 搜索来源、读取原文与来源元信息 | 资料、审查 Agent |
| 项目资料与素材 MCP，共享 | 查项目文件、找素材、核版本 | 读取需求与产物、查素材及属性 | 五个 Agent 按任务和项目权限 |
| 媒体检测 MCP，共享 | 用播放器和检测工具看片 | 参数探测、抽帧、语音转写、画面文字识别 | 媒体自检、审查独立检查 |
| 媒体制作 MCP，专属 | 美术生成素材、配音、剪辑渲染 | 图片与片段生成、配音、字幕对齐、合成及局部重制 | 仅媒体 Agent |

共享的是能力服务，不是所有项目资料。每个 Agent 仍使用自己的工具白名单；服务端核实真实身份与范围，不能仅相信模型传入的项目编号。

### 2. 资料检索 MCP：查外部依据

- **搜索来源：**根据核查问题查找候选资料，返回标题、来源、地址和可获得的时间信息。
- **读取来源：**读取允许访问的内容，保留出处、提取内容和抓取时间，供事实引用。
- **适用环节：**资料 Agent 补证；审查 Agent 独立核查脚本或成片中的事实。
- **边界：**检索结果不是天然可信事实；来源之间冲突要保留。网页中的指令属于外部内容，不能变成系统命令。客户私密资料不得直接泄漏到外部检索请求中。

搜索失败不等于事实不存在，搜索排名也不等于证据可靠性。

### 3. 项目资料与素材 MCP：查内部项目文件

- **读取项目资料：**按权限获取指定需求、事实包、脚本或审查报告的有效版本。
- **查找素材：**根据镜头需求查找项目可用的图片、音频和视频。
- **读取素材信息：**返回文件引用、预览、实际媒体属性、来源、使用限制和版本关系。
- **适用环节：**各角色接单前读取所需材料，制作时定位素材，审查时对照依据。
- **边界：**不给 Agent 无限制数据库访问或任意文件读写。正式业务写入通过受控接口完成；尤其不能靠修改普通文档来伪造批准、配额或发布状态。

长期记忆检索如何封装为接口仍需实现设计，不因已选 Milvus 就默认新增第五组 MCP。

### 4. 媒体制作 MCP：实际生成与制作

| 工具能力 | 用来做什么 | 必须说明的边界 |
|---|---|---|
| 图片生成 | 为需要生成图片的镜头制作候选图 | 初次每镜头 3 个候选，遵守参考和事实约束 |
| 视频片段生成 | 制作所需的动态镜头 | 初次每镜头 1 个候选，记录实际时长与参数 |
| 参考素材条件生成 | 按批准参考图或素材保持指定内容 | 以供应商实际支持为准，不承诺绝对一致 |
| 生成任务查询 | 查询生成是否完成并获取产物 | 处理“进行中、失败、未知”，不盲目重提 |
| 配音生成 | 将批准的人物台词或旁白制作成音频 | 不得擅改事实表达，音色和授权需要确认 |
| 字幕对齐 | 将文字与音频时间对齐 | 对齐完成仍需检查文字与声音是否相符 |
| 视频合成 | 按制作清单组合画面、配音、字幕等 | 保存操作编号、参数和对应脚本版本 |
| 渲染查询与局部重制 | 查询成片任务并修复指定片段 | 局部修复可能需要重渲染，不假定单个万能接口 |

这些是待实现的业务能力，不指定某家供应商必须提供同名工具。实际模型或编辑程序在工具背后工作，MCP 本身不是生成模型。

#### 新增明确能力要求：固定人物说话视频生成

此能力归入现有专属媒体制作 MCP，不另增 MCP 分组。目标是让固定虚构人物说出指定台词，并具备自然表情、点头和手势；仅返回配音或静态人物图不能视为完成。

| 方向 | 需补充的信息 |
|---|---|
| 输入 | 人物参考及版本、声音设定、批准台词；采用音频驱动时提供台词音频及版本 |
| 输入 | 任务与镜头关联、自然表达要求、输出规格；不默认要求商品操作或精准动作 |
| 输出 | 人物视频片段引用、实际参数、操作状态、使用的人物与脚本及音频版本、可获得的用量费用 |
| 失败与不确定 | 不支持的动作或输入应说明；口型、人物或自然度无法达标时返回问题，不伪报成功 |

模型、供应商、是否需要独立口型或动作处理均未选定。“人物参考＋音频 → 说话视频”只作为建议验证路线。媒体检测 MCP 的人物与口型检查能力同样需验证，不预先宣称存在已接入的万能检测工具；保留人工复核和检查覆盖范围。

### 5. 媒体检测 MCP：提供检查证据

| 工具能力 | 大白话 | 返回结果 |
|---|---|---|
| 媒体参数探测 | 看文件真实规格 | 实测时长、尺寸、音视频轨等 |
| 视频抽帧 | 按时间取画面检查 | 带时间位置的图片引用 |
| 语音转写（ASR） | 听视频里实际说了什么 | 转写内容及可获得的时间信息 |
| 画面文字识别（OCR） | 看字幕、包装和画面上写了什么 | 文字、位置及可获得的置信信息 |

媒体 Agent 用这些工具自检，审查 Agent 用它们独立复核。识别结果也可能出错，工具只给证据，不能保证事实正确、素材有使用权或必然符合平台要求。

### 6. AI 素材允许生成什么？

已确认纳入 AI 图片和视频片段生成，但不是所有画面都可以自由编造。

- 本轮明确允许制作 AI 虚构成年女性讲解者，按确定的人物方向跨视频复用；形象、声音与素材来源仍需记录，不以复刻真人为目标。
- 背景、创意表达、知识说明性画面等，可以在需求与约束允许时生成；生成画面不是证明知识结论的事实依据。
- 商品营销仅为参考扩展场景；若实际涉及商品，真实外观、包装、品牌标识、规格和宣传事实仍以确认资料为准，缺少关键参考时先补资料。
- 不能凭想象生成商品内部结构、虚构真实效果，或把合成新闻画面当作真实现场。
- 用户提供或外部取得的素材也要检查来源与适用范围，不能因“文件已经上传”就推断具有全部使用权。

### 7. 媒体工具输入与输出约定

媒体 Agent 从批准脚本和项目资料整理参数，普通用户不必手填全部技术字段。

| 方向 | 必要信息 | 用途 |
|---|---|---|
| 输入 | 任务、镜头、脚本版本关联 | 知道为哪条视频、哪个镜头制作 |
| 输入 | 画面目标、风格、批准参考素材 | 说明想要什么，而非只有一句泛化提示词 |
| 输入 | 不可改变的知识事实、人物与内容约束，以及适用品牌规则 | 防止生成时改变知识含义、讲解者或实际涉及的商品 |
| 输入 | 输出尺寸、比例、时长等适用规格 | 为后续合成提供可用结果 |
| 输出 | 进行中、完成、失败或未知等状态 | 区分受理与真实完成 |
| 输出 | 操作编号、产物引用及预览 | 可查询、可追踪、可检查 |
| 输出 | 实际媒体属性及任务、镜头、脚本、参考版本 | 验证实际结果，而非只复制请求参数 |
| 输出 | 错误信息、可获得的用量、费用与耗时 | 排障、预算管理与指标统计 |

拿不到的费用或状态明确记为未知，不能填零冒充已测量。大文件放文件存储，交接引用和必要摘要，不把视频本体塞入上下文。

### 8. 候选选择和自动修改的最新规则

```text
批准脚本与制作清单
        ↓
需要图片的镜头：初次各 3 个候选
需要视频片段的镜头：初次各 1 个候选
        ↓
媒体 Agent 初筛、提出建议 → 审查 Agent 检查
        ↓
合格素材进入合成；不合格则检查阶段与全任务额度
        ↓
允许返工：集中修复本轮问题 → 复查
        ↓
仍不合格 / 超限 / 无法判断：转人工
        ↓ 素材及制作条件满足后
首次合成 1 条完整视频 → 自检与独立审查
        ↓
必要时在额度内局部修复 → 提交预览 → 人工审批 → 最终交付
```

默认由媒体 Agent 初筛、审查 Agent 检查，不要求用户每次在三个候选里手动选图；主观偏好不明确、存在争议或需要超额处理时才交人工。

| 阶段 | 初次产出 | 本任务该阶段自动返工上限 | 修改范围 |
|---|---|---|---|
| 资料整理 | 首次事实包 | 1 轮 | 补充已定位的资料问题 |
| 脚本创作 | 首稿 | 1 轮 | 修改问题段落及受影响镜头 |
| 图片素材生成 | 每个需生成图片的镜头 3 个候选 | 1 轮 | 优先修改选中候选；全部不合格时，每个受影响镜头生成 1 个修正版 |
| 视频片段生成 | 每个需生成片段的镜头 1 个候选 | 1 轮 | 修复或重制受影响镜头 |
| 成片合成 | 1 条完整视频 | 1 轮 | 修复受影响的画面、声音、字幕或合成问题 |

**全任务各阶段自动返工累计最多 4 轮；阶段上限和总上限必须同时满足。** 五个阶段各有一轮机会，不表示五轮都能用。例如资料、脚本、图片、片段都返工过，已累计四轮，成片出现新问题也必须转人工。

“本任务图片阶段一轮”不等于“每张图片都能各开一轮”。一轮绑定确定的问题清单与受影响镜头，可以集中处理多个问题；不能不断追加新问题让这一轮永不结束。初次生成三个候选不算三轮返工，失败后也不能重新生成三套候选绕过限制。

人工意见引发的自动修改同样占用额度；改版本、换 Agent、断线恢复或跨阶段回退均不重置。自动修复后仍不合格，交付已有产物、问题、证据、已尝试动作及用量，等待人工处理。

#### 人物讲解的额度补充与待定边界

既有候选数量、阶段返工和全任务总上限不变。固定人物的参考应被复用，不能以每个镜头重新设计人物的方式绕过额度；“每镜头初次 3 个图片候选”只针对确实需要生成图片的镜头，不要求每个镜头重新选一张人脸。

**建议、尚未定稿：**人物说话片段归入视频片段阶段；若改配音导致重做人物片段，将其作为一次关联修复计入该阶段，而不是额外获得声音修改轮数。具体计数归属、人物首次建立的额度范围及跨阶段关联修复规则仍需明确，不能将本段当作已批准的独立预算。明确前遇到无法归类的修改，交主管请求人工处理，不自行增加额度。

人物说话能力不新增第六个自动返工阶段。阶段和全任务既有约束始终有效，内容质量问题不得伪装成技术失败重试。

### 9. 技术重试不是内容返工

- **技术失败：**同一逻辑操作首次失败后，最多额外重试 2 次，即最多 3 次尝试；仅对适合重试的临时错误使用。
- **内容不合格：**人物片段生成成功但台词、口型或人物形象不符合要求，属于内容返工，不能伪装成网络重试增加轮数；商品场景中的商品画错同理。
- **结果未知：**先按操作编号查询与核对，确认没有成功或可安全重试后再处理；禁止因超时直接重复生成、扣费或发布。
- **统一计数：**SDK、MCP、工作流与主管不能各自再套一组重试，次数必须汇总到同一逻辑操作。
- **人工接管：**权限错误、关键参数问题、预算不足、额度耗尽等，不允许无限重试。金额和调用量硬上限的具体数值仍待确定。

### 10. 抖音发布：手动和系统代发都保留

这是创作交付之后的独立受控能力，不改变“5 个 Agent、7 个 Skills、4 组创作 MCP”的已确认结构。发布接口封装、模块归属及发布文案由谁准备仍需明确，不能宣称已经新增运营 Agent 或接通发布 MCP。

```text
成片已获正式批准，交付对应版本
                  ↓
           用户选择发布方式
        ┌─────────┴─────────┐
        ↓                   ↓
     手动发布             系统代发
下载视频和发布文案     选择已授权账号
用户自行上传抖音       预览标题与发布设置
回填链接或作品编号     用户单独确认发布
记录并核实状态         受控接口提交并获取回执
        └─────────┬─────────┘
                  ↓
       核实是否实际公开，保存证据
                  ↓
       在约定窗口采集可获得的数据
```

- **已确认：**两种方式都支持；成片审批不是发布授权；代发必须单独确认。
- **能力前提：**系统代发仅在具备实际可用的官方接口能力和有效账号授权时执行，能力与授权范围尚需核实。
- **状态原则：**用户说已发布、接口受理或上传成功，都不直接等于确认公开；无法核实时保留待核实状态。
- **建议的记录设计：**以账号、成片版本和发布意图关联一条逻辑发布记录；保存方式、回执或链接、状态、核实来源与时间。
- **防重复原则：**结果未知时不自动换一种方式再发；手动与代发分别展示，汇总时同一次逻辑发布只算一次。

发布后的观看与互动数据以实际可取得的授权数据或用户提供的后台记录为准，不能假定所有指标都有接口、实时性或统一口径。

## 第七题：评估指标有哪些？预期达标值是什么？

### 1. 已确认的指标分层

采用之前讨论的 **“一、底线指标；二、六个核心指标；四、辅助观察与诊断指标”**。保留这个分类名称是为了对应原讨论，并不是本文漏了一类。

大白话：**先看有没有犯不能犯的错，再看能否省事交付和取得观看效果，最后用辅助指标查原因。** 不把订单、销售额或商品转化列为本项目核心目标。

目前确认了 **3 项底线要求与 3 个核心指标的数值目标**。其余三个核心指标已确定要看，但目标尚未确认；所有真实结果均为**未采集／尚未评估**，不是已经达标，也不能显示为零。

### 2. 底线指标：三项验收要求

| 指标 | 大白话 | 已确认目标 | 检查与报告口径 |
|---|---|---|---|
| 关键事实错误 | 不编造知识，不遗漏关键适用条件，不把虚构当事实；涉及商品时不编属性 | 人工复核验收测试集中 0 项 | 报告关键错误数、视频样本数、事实核查项数及不确定内容 |
| 审批与权限违规 | 不越权读取，不跳过审核，不擅自发布 | 专项测试中 0 次 | 覆盖权限隔离、版本失效、未批准交付与未单独确认发布等路径 |
| 执行失控 | 不超额返工，不无限重试，不重复执行 | 专项测试中 0 次 | 检查阶段与总额度、重试、未知结果、重复提交和暂停恢复 |

这些零是**目标**，只在明确的测试集和覆盖范围内验收，不是“生产环境永远不会出错”的承诺。发现问题要修复并重新验证，不能用高完成率或播放量抵消底线违规。样本数量与具体测试计划尚未确认。

### 3. 六个核心指标总表

| 核心指标 | 大白话 | 预期达标值 | 确认状态 | 实际结果 |
|---|---|---|---|---|
| 创作任务完成率 | 交给系统的任务，有多少按约定交付 | ≥90% | 已确认 | 未采集 |
| 首次人工通过率 | 第一次给人看成片，有多少直接通过 | ≥80% | 已确认 | 未采集 |
| 单条合格视频总成本 | 为交付一条合格视频，总共花了多少钱 | 数值上限待定 | 指标已确认，目标待定 | 未采集 |
| 人工投入下降比例 | 相比纯人工，实际少花多少人工时间 | ≥30% | 已确认 | 未采集 |
| 公开发布达成率 | 计划发布的视频，有多少核实已公开 | 目标和观察窗口待定 | 指标已确认，目标待定 | 未采集 |
| 完播率 | 实际观看中，有多少按采用口径看完 | 目标待定 | 指标已确认，目标待定 | 未采集 |

以上是本项目目标，不是抖音官方标准。曾讨论过的“完播率提升 3 个百分点”等数值没有确认，不能写入正式达标值。

### 4. 核心指标怎样计算？

以下为指标落地时的统计口径说明；统计周期、时间与费用预算、样本规则等尚未确定的参数，需要在正式评估前固定，不能看完结果再修改分母。

| 指标 | 计算口径 | 必须保留的边界 |
|---|---|---|
| 创作任务完成率 | 约定时间和额度内，最终批准并交付的合格创作任务数 ÷ 有效任务数 | 正常人工审批允许；转人工接手制作完成，不能算系统自动完成；发布另算 |
| 首次人工通过率 | 首次成片预览直接获批的任务数 ÷ 首次人工审核已有决定的任务数 | 待审核单独列出，不当失败；内部自动返工次数同时披露，不冒充第一次生成就通过 |
| 单条合格视频总成本 | 同批次约定范围内全部成本 ÷ 合格交付视频数 | 包含失败候选、重试、返工和人工成本；明确基础设施分摊方式；没有合格交付时不能算零成本 |
| 人工投入下降比例 | （可比纯人工基线工时 − 使用系统后的人工工时）÷ 纯人工基线工时 | 对齐复杂度和质量，计入审核、沟通及异常接管；无人等待机器的时间不计人工工时 |
| 公开发布达成率 | 截止观察时点已核实公开的逻辑发布数 ÷ 截止该时点应完成的计划发布数 | 手动与代发分列并去重；待核实不算已公开；自愿不发布的创作任务不自动进入分母 |
| 完播率 | 按实际可取得的抖音数据定义，统计完整播放对应比例 | 优先保留来源原定义；缺少兼容的分子分母时不自行拼算；对比需保持时长、主题和观察窗口可比 |

所有比率在分母为零或数据缺失时显示“暂不可计算”，并说明原因，不用 0% 代替未知。真实评估还应报告统计窗口、样本量和数据来源。

### 5. 辅助观察与诊断指标

| 类别 | 建议记录的指标 | 用来解释什么 | 数值目标状态 |
|---|---|---|---|
| 工具稳定性 | 首次成功率、重试后最终成功率、错误类型、重试次数 | 卡在工具本身还是内容质量 | 未确认 |
| 处理耗时 | 阶段耗时、总耗时、中位数与 P95；人工等待分列 | 慢在生成、渲染、排队还是审批 | 未确认 |
| 记忆检索 | 标注问题的有效检索命中率、权限与失效内容过滤情况 | 是否找回正确且允许使用的经验 | 未确认 |
| 观看与互动 | 播放量、平均观看时长、点赞、评论、分享 | 发布后观众是否感兴趣 | 未确认 |
| 可追溯性 | 事实来源、脚本与成片版本、审批和工具记录关联完整情况 | 出问题能否定位原因及责任环节 | 未确认 |

可采用的统计方式仍需明确：例如记忆检索用 Hit@5，要先有标注的查询与相关结果；互动率可按“点赞＋评论＋分享”除以播放次数观察，但这不是去重互动人数，也不宣称是平台唯一官方定义。中位数代表典型耗时，P95 可用来观察较慢的那部分任务。

不将曾提出的工具成功率 ≥95%、记忆命中率 ≥90%、可追溯性 100% 等建议写成已确认验收目标。追溯记录缺失应提示并处理，不因尚未设定百分比而取消必要的版本、审批及证据校验。

### 6. 数据从哪里来？怎样避免误判？

- **业务记录：**读取 PostgreSQL 中的任务、产物版本、正式审批和发布状态，不能只统计 Agent 的自然语言汇报。
- **执行记录：**保留操作关联、开始结束时间、结果、实际用量与返工重试计数，避免一个操作被多层重复统计。
- **人工投入：**记录纯人工基线与系统辅助时的实际人工工时，明确估算部分及统计边界。
- **抖音表现：**通过确实可用且已获授权的接口，或用户提供的后台数据获取；保存账号、作品、时间窗口和来源。权限不足显示不可获取，不造数。
- **比较条件：**尽量对齐账号、主题、时长和观察窗口，付费与自然流量分开，结合样本量与中位数看趋势；前后对比不直接证明效果由系统单独造成。
- **状态区分：**目标值、实际值、数据是否完整、是否达标分别显示；没有采集数据时状态是尚未评估。

### 7. 已确认与待讨论的边界

**已确认：**指标三层结构、三项底线、六个核心指标，以及完成率 ≥90%、首次人工通过率 ≥80%、人工投入下降 ≥30%；支持手动与系统代发，两种方式分列并去重统计。

**待确定：**单条成本上限、公开发布达成率目标与观察窗口、完播率基线和目标、辅助指标阈值、样本与测试集、评估周期、真实数据接入和人工工时记录办法。

当前只更新指标定义与已确认目标，不把此前建议的样本规模或专项测试安排当作已获同意的执行计划，也不表示后台已完成埋点或已采集到结果。

### 8. 人物知识讲解的新增质量检查项

本轮补充质量要求，不替换六个核心指标，也不改变已确认的 ≥90%、≥80%、≥30% 目标及三项底线。以下检查项需要纳入审查与后续评估；具体测量方法、自动化覆盖范围和数值阈值尚未确定，真实结果未采集。

| 检查项 | 大白话与检查重点 | 边界 |
|---|---|---|
| 知识准确性 | 讲解有依据，概念、条件和例子不误导 | 纳入已有关键事实底线，不另造一个未经确认的百分比 |
| 讲解清晰度 | 台词适合口述，解释和例子容易理解，节奏合理 | 可结合人工评审；目标受众与具体评分办法待定 |
| 台词准确性 | 不漏说、错说或擅自加话，字幕与实际内容对应 | 转写可能有误，疑点回听核实 |
| 口型同步 | 嘴部动作与实际语音协调 | 检测工具和阈值待验证，不能只靠几张抽帧判定 |
| 人物一致性 | 跨镜头与跨视频保持固定讲解者的可辨识形象 | 对照有效人物参考版本；不要求未确认的服装背景永久固定 |
| 声音一致性 | 同一讲解者符合设定，避免片段间突兀变声 | 风格已确认，具体固定音色和技术绑定待定 |
| 动作与表情自然度 | 点头、手势和表情自然，不明显异常或干扰讲解 | 不考核精准指向、拿物品等未要求的动作 |
| 声画与辅助内容配合 | 配图、示意图和字幕与讲解含义对应 | 辅助画面按需使用，不要求每条视频形式相同 |

人物与声音及参考素材的来源、适用范围和版本属于业务校验，不与画质混成一个综合分数；审查结论不能替代人工批准。口型通过不代表知识正确，生成成功不代表视频合格。


## 总结

**业务层面：**Live Make 既有企业内部内容团队定位不变，当前核心为固定 AI 虚构人物的知识讲解视频。人物为写实、美丽性感成熟的成年女性，声音成熟温暖清晰自然，配合自然表情、点头和手势；不默认商品展示或精确动作。原三家公司保留为业务参考。批准交付后，可手动发布或单独确认系统代发到抖音。

**架构层面：**以 DeepAgents 为目标编排框架，采用 **1 个主管＋4 个专业子 Agent、7 个 Skills、1 组专属＋3 组共享创作 MCP**。主管自主组织工作，权限、版本、审批和预算由程序约束；不把广义 A2A 协作混同为已接入 A2A 标准协议。

**制作层面：**需要生成图片的镜头初次各 3 个候选，需要生成视频片段的镜头初次各 1 个候选。资料、脚本、图片、片段和成片合成各最多自动返工 1 轮，全任务累计最多 4 轮；同一操作额外技术重试最多 2 次，达不到要求就转人工。

**数据层面：**短期 Redis；中期 PostgreSQL 项目记录；长期 PostgreSQL 原文及有效性记录＋Embedding＋Milvus 向量检索；实际媒体使用文件存储。正式审批和状态不能用记忆摘要替代。

**效果层面：**三项底线目标为相应验收测试范围内关键事实错误、审批权限违规和执行失控均为零；核心数值目标为完成率 ≥90%、首次人工通过率 ≥80%、人工投入下降 ≥30%。这都是预期目标，实际数据尚未采集，其余核心目标待定。

**后续待定：**具体人物参考与音色、人物记录字段与预览审批方式、人物制作模型和是否需额外口型处理、声音与片段关联修复的计数归属、人物质量检查方法与阈值，以及原有模型与工具供应商、发布模块归属、Embedding、部署与保留期限、审批细节、费用和调用量上限、其余指标目标与评估方案。已确认完整目标方向不等于当前代码已经全部实现；后续逐项讨论，不擅自扩大本次文档更新为功能开发。
