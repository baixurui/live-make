# 发布联调修复规格、设计与验收

用户授权：补齐业务上下文接口、统一版本类型和事件字段，本模块重试一次，工作流收到最终失败转 PAUSED，并创建修复 PR。

## 范围与设计

基于 main 的发布模块合入 PR #18 工作流及其业务 API 依赖，在独立分支上联调；不合并远程 main。

- 业务 API 提供独立 Bearer 服务凭据保护的 publishing-context 端点。从同一数据库的工作流记录、当前媒体/脚本和真实审批投票生成上下文；每次查询重新检查启用审核人、版本和风险。快照读取要一致，不使用请求自报审批。
- 媒体版本统一为正整数。发布请求、回执、上下文、共享 Schema 和测试全部同步。既有模拟数据库若保存字符串版本，启动前须使用新数据库；不猜测字符串到业务版本的映射。
- 发布失败事件增加 request_key（等于原发布请求幂等键），保留 receipt_id；attempt 是发布器实际调用次数 0–2，retryable=false。工作流按发布专用规则匹配 active_request_key、receipt_id 和最终事件；不套用其他节点的零基重试编号。
- 工作流发布请求使用逻辑发布键，不按尝试生成新键。拒绝可重试的发布失败事件；保留其他节点的重试机制。
- 提供工作流 HTTP 发布适配器：投递并在持久受理后确认请求，拉取结果、原子应用状态与 inbox 去重、最后确认发布端事件。传输错误只重投相同请求，不能增加业务重试次数。
- 两个服务独立连接业务数据库；HTTP 服务读取和写入在连接级锁内执行，避免共享连接线程交错。

## 执行任务

1. 解决共享 OpenAPI 合并冲突，保持两侧端点。
2. 实现可信上下文与服务认证，规范版本类型，更新契约导出。
3. 修改工作流最终发布事件处理与逻辑幂等键，增加 HTTP 适配器及 CLI。
4. 使用真实业务 HTTP 服务、真实发布 HTTP 服务和真实工作流跑三类发布结果，验证重放、确认中断、认证及审批撤销。
5. 跑业务 API、工作流、发布、契约回归，记录结果；提交推送并创建 PR，注明 #18 依赖。

## 验收标准

- 初次成功与重试成功 → 工作流 PUBLISHED；两次失败 → PAUSED，总发布尝试为 2，后续 tick 不再次发发布请求。
- 失败事件 request_key/receipt_id 不匹配、retryable=true 或无效 attempt 不得更改任务状态。
- 重复投递、结果确认丢失、工作流重启后仍只有一个逻辑发布及一份有效结果状态迁移。
- 无服务凭据、仅伪造内部服务头、用户会话不能访问上下文；旧版本审批、被停用审核人、变更风险或缺失业务记录不能放行。
- 所有已纳入模块的自动化回归通过。媒体生产未纳入依赖，现有媒体集成测试如跳过必须明确记录。

## 验证结果（2026-09-22）

- 真实 HTTP 集成测试：8/8 通过；使用实际 BusinessApi、HttpTaskSource、FastAPI、Workflow 与稳定散列模拟器。
- 发布模块：31/31 通过；共享契约：3/3 通过。
- 业务 API：7/7 通过；工作流：24 项通过，2 项媒体生产集成测试因缺少 MEDIA_PRODUCTION_SRC 显式跳过。
- 合计 73 项通过、2 项跳过。Ruff 检查本次新增/修改模块通过。
- 本地连续两次失败已实际更新业务 tasks 表为 PAUSED，后续 tick 无再发布；结果确认丢失后重启仅产生一次 PAUSED 状态迁移。
- 前端、真实部署凭据与网络、媒体生产全链路未在此次验收中覆盖。原有业务 API 的其他内部接口仍采用已有 header 身份设计，本次只为新增发布上下文提供专用凭据。
