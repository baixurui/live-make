# 模拟发布、指标与看板接口 Spec

状态：负责人已授权按规格推进实现，并确认本模块负责一次重试、工作流负责转 PAUSED；其他模块的真实联调仍需各负责人配合。

需求来源：https://github.com/baixurui/live-make/issues/14

## 背景

项目已有共享 API、事件和状态枚举，本模块负责消费工作流的发布请求，执行模拟发布，保存唯一回执，生成指标快照，并提供最近 7 天的看板数据。

当前骨架尚未定义工作流身份验证、审批信息读取、完整指标响应及重试责任。本文将 Issue 的明确要求与建议协作约定分别记录，作为后续技术设计的依据。

## 目标

- 跑通已审批、已排期任务的模拟发布闭环，并支持重复投递、失败和恢复。
- 产生可重复验证的模拟结果和指标，保证看板统计不重复计数。
- 将模拟发布行为与内部回执分离，使未来官方发布适配器可以复用回执语义。
- 允许通过受控的依赖替身独立验收，联调时接入真实工作流和业务数据。

## Issue 明确要求

- 仅消费工作流在北京时间 12:00 发送的已排期发布请求。
- 默认成功，10% 概率可复现失败；首次失败自动重试一次，仍失败转 PAUSED。
- 同一幂等键产生唯一回执与唯一结果，不重复发布。
- 成功作品在发布后 1 小时、24 小时、7 天生成快照。
- 指标依据质检和审核信息生成，有规律但不保证爆款；聚合播放、点赞、评论、收藏、转发、涨粉和发布成功率。
- 最近 7 天聚合正确，遵守 1 周保留要求。
- 不接入真实抖音 OAuth 或发布，不自动调整策略，不允许浏览器直接发布。

## 建议协作约定

以下是为消除歧义提出的具体口径，不代表团队已有共识。确认后的变更需要同步到共享契约及相关生产方、消费方。

| 编号 | 建议约定 | 对接方 |
| --- | --- | --- |
| D1 | 工作流负责北京时间 12:00 的触发；消费者允许同一北京时间日期内的延迟投递，拒绝提前执行和跨日首次执行。终态请求的合法重放只读取原结果。 | 工作流 |
| D2 | 工作流身份来自可信传输身份或服务凭据；审批、排期、账号和媒体版本来自可信业务记录，不能只相信请求自报字段。读取失败时停止发布，不按已审批处理。 | 工作流、业务 API |
| D3 | 本模块负责一次自动重试；工作流不额外重试发布操作，负责根据结果更新全局任务状态。持续失败时本模块保存终态失败并可靠通知工作流转 PAUSED。 | 工作流 |
| D4 | 10% 指每次模拟调用的失败概率；同一模拟种子、幂等键和尝试次数对应稳定结果。重试采用下一次尝试编号，允许重试成功或连续失败。 | 工作流、模块负责人 |
| D5 | 最近 7 天指查询时刻向前 168 小时，包含起点、不含终点；作品按成功发布时间归属。每件作品取查询时刻可用的最新累计快照再求和，未生成快照的作品贡献零指标。按日展示时使用北京时间日期，边缘日期可为不完整自然日。 | 前端 |
| D6 | 发布成功率按窗口内首次合法受理的逻辑发布任务统计：成功数 /（成功数 + 两次失败后暂停数）。处理中任务单列并排除分母；拒绝请求、事件重放和重试次数不增加分母；分母为零时返回空值。 | 前端、工作流 |
| D7 | 1 周保留从快照实际生成时刻计时，保留 168 小时；第 7 天快照照常生成，再按自身生成时间保留。清理不删除幂等凭据和最终回执；这些记录本期持续保留，另行约定归档期限。 | 业务 API、模块负责人 |
| D8 | 本模块保留请求中的回执标识并验证一致性；工作流提供任务、账号、排期、审批对应媒体版本及质检/审核评分。具体读取方式、身份机制和缺失字段在技术设计及共享契约中落实。 | 工作流、业务 API、媒体生产 |

## 功能需求

### F1：校验发布资格

- 只接受可信工作流提交、符合共享契约的发布请求。
- 首次执行前核实任务已完成必需的审批、当前允许发布、已排期且已到执行时间，并确认媒体版本与审批记录一致。
- 风险阻断、审批撤销、任务取消或暂停时不得执行发布。首次执行及自动重试均重新核实资格。
- 排期遵守北京时间每天 12:00、单账号每天最多一条的项目约束；拒绝同一账号同一排期日的第二个逻辑发布任务。
- 提前、跨日、缺失信息、身份不符或无法验证的请求均不得调用发布器；给出可区分的拒绝或依赖不可用原因。
- 全局任务可能已进入发布中状态；具体允许状态与工作流对齐，不能简单要求始终停留在已排期状态。

### F2：持久化幂等与唯一回执

- 同一幂等键只对应一个逻辑发布任务、一个回执和一个最终结果。
- 相同请求重复或并发到达时复用已有处理记录；处理中返回处理中状态，终态返回已保存结果。
- 同一键关联不同任务、回执、账号、媒体版本或排期时拒绝冲突，不覆盖原记录。
- 同一逻辑发布使用不同幂等键重放时也不得重复发布，需通过业务唯一性约束拒绝或识别为已有任务。
- 进程重启后仍能识别已有发布和剩余尝试次数；不得因为重投、恢复或并发处理增加实际发布次数。
- 每次调用都可追溯到原始请求、关联标识、逻辑发布、回执和尝试编号；处理中状态不被冒充为最终结果。

### F3：可复现的模拟发布与一次重试

- 按 D4 生成约 90% 成功、10% 失败的模拟调用结果；有限批次不要求恰好 10% 失败。
- 首次模拟调用失败后自动重试一次，总调用次数最多两次。身份或业务资格不合法不属于可重试的模拟失败。
- 两次调用之间保留尝试记录；重启、事件重复投递和多个消费者不能重置重试额度。
- 成功后保存稳定的平台作品标识、成功时间和回执，后续重放返回同一结果。
- 重试前若资格被撤销，不再调用发布器，记录明确的终止原因并通知工作流；不能误报成功。
- 两次模拟调用均失败后，保存终态失败并通知工作流转 PAUSED。工作流状态尚未确认时保留可恢复的通知记录。

### F4：可靠回传与适配器边界

- 成功和失败结果遵守共享事件契约；事件关联信息与原请求一致，尝试编号和是否可重试的语义一致。
- 本地结果保存后，即使结果通知失败或进程重启，仍能恢复通知；重复通知不导致工作流重复执行发布或覆盖终态。
- 内部回执能表达逻辑发布、发布目标、成功或失败、平台作品标识、时间和错误信息，不要求调用方理解模拟算法。
- 后续替换发布适配器时，调用方无需改变回执的业务含义；本期不承诺真实外部平台的幂等能力。

### F5：生成三阶段指标快照

- 仅为成功发布的作品安排发布后 1 小时、24 小时和 7 天的快照，未到时间不生成。
- 同一作品同一阶段最多保存一份快照。重复调度和重启恢复不能创建重复记录或改变已保存结果。
- 调度延迟或服务重启后补齐已到期阶段，区分计划采样时点和实际生成时刻。
- 快照包含播放、点赞、评论、收藏、转发和涨粉的累计值；均为非负整数，同一作品后续阶段的累计值不低于前一阶段。
- 模拟数据依据已固定的质检/审核输入与稳定种子生成；评分较好可改善总体分布，但不保证每件作品超过低评分作品。
- 缺失用于模拟指标的评分时采用明确的中性基准并记录降级原因；不因此改变发布审批结论。

### F6：最近 7 天看板数据

- 通过共享契约已声明的指标查询能力提供 D5 的六项聚合指标和 D6 的发布成功率。
- 同时提供窗口边界、统计时刻、成功数、终态失败数、处理中数及已有快照的作品数，便于前端解释数据。
- 提供按北京时间发布日期归属的作品指标汇总，以及按首次受理日期归属的发布成功率统计；两者不能混用时间归属。
- 使用每件作品的最新累计快照，禁止把三个阶段的累计量相加；事件重复投递、重试和重复生成不能放大统计值。
- 空窗口返回零计数、零累计指标和空成功率；查询遵守业务 API 的账号可见范围，不泄露未授权账号数据。

### F7：保留与清理

- 按 D7 清理过期指标快照；查询不得返回已经超过保留时长的快照，即使后台清理尚未执行。
- 尚未到期的快照计划、第 7 天快照生成及去重不因指标清理被破坏。
- 清理不能删除保障幂等、回执重放和结果通知恢复所需的信息；清理后重放历史请求不会重新发布。

## 非功能需求

- N1：所有跨模块交互以共享契约为唯一来源，新增字段、响应和状态语义须同步生产方、消费方和契约测试。
- N2：发布与统计可在本地使用受控依赖替身验收，不依赖真实抖音账户或外部媒体发布能力。
- N3：时钟和模拟输入可控，测试不需要真实等待 1 小时或 7 天；重启和并发场景可验证。
- N4：服务凭据从运行环境获取，不提交密钥；日志不输出凭据，能通过关联标识追踪发布与通知。
- N5：身份、审批或持久化依赖故障时不继续未经验证的发布；恢复后不重复已完成操作。
- N6：时间比较采用明确时区的时间点；日排期与日期展示按 Asia/Shanghai 解释。

## 不做的事

- 真实抖音 OAuth、上传和发布，以及其他真实平台的接入。
- 浏览器直接触发发布、自动策略调整、补发新任务或人工重试入口。
- 接管工作流的全局状态机、每日选题、脚本生成、视频制作和审核界面。
- 重新定义共享风险等级，或在本模块单方面改动其他模块的接口。
- 实现长期历史分析和回执归档策略。

## 验收标准

| 编号 | 覆盖 | 可观察的验收行为 |
| --- | --- | --- |
| AC1 | F1 | 有效的工作流请求、审批和排期可执行；非工作流、未审批、未排期、提前、跨日首次执行、版本不一致和风险阻断均不调用发布器。 |
| AC2 | F1、F2 | 同账号同排期日的不同任务并发提交，最多一个获得执行资格；相同任务换键也不能再发布。 |
| AC3 | F2 | 相同请求串行、并发重放及重启后重放，得到同一回执和最终结果；首次成功场景发布器只调用一次。 |
| AC4 | F2 | 同键不同任务或关键业务内容得到冲突响应，原回执、结果和尝试次数保持不变。 |
| AC5 | F3 | 固定测试输入分别稳定复现首次成功、首次失败后成功、两次失败；跨进程重复运行结果一致。大样本模拟失败比例按预先规定的容差接近 10%。 |
| AC6 | F3 | 两次失败后不再调用发布器，工作流最终可观察到 PAUSED；在首次失败后重启或重投也最多调用两次。 |
| AC7 | F1、F3 | 首次失败后撤销审批，自动重试不再发布，记录终止原因并向工作流回传。 |
| AC8 | F4 | 结果通知失败后恢复，最终通知能送达；重复通知不会产生第二次发布。成功、失败事件均通过共享契约校验。 |
| AC9 | F4 | 用另一受控发布适配器返回成功或失败，调用方仍能读取相同语义的内部回执。 |
| AC10 | F5 | 推进时钟验证三个阶段：到期前无快照，到期后恰好一份；重启、重复执行和延迟补齐后没有重复快照。 |
| AC11 | F5 | 固定评分与种子的结果可重现；累计值非负且逐阶段不减；固定批次评分对照体现分布规律，缺失评分使用中性基准且可追踪。 |
| AC12 | F6 | 为同一作品准备累计播放量 100、300 的两份有效快照，聚合贡献为 300；其他指标也取最新快照而非相加。 |
| AC13 | F6 | 窗口内两个成功任务、一个两次失败任务和一个处理中任务，成功率为 2/3；重试和重放不改变分母；空数据成功率为空。 |
| AC14 | F6 | 验证滚动窗口起点包含、终点排除，以及北京时间跨日分组；越权账号数据不可见；没有快照的成功作品仍计入发布成功数。 |
| AC15 | F5、F7 | 第 7 天快照可生成，并按自身生成时间保留 168 小时；到期后查询排除且清理可删除；清理后重放原请求不再次发布。 |
| AC16 | F1–F7 | 使用工作流和业务数据替身走通合法请求、唯一发布回执、结果通知、三阶段快照和看板查询，再通过真实模块联调验证相同流程。 |
